# Weapon workshop

For server-free GitHub Pages hosting, run `python tools/build_github_pages.py`.

Generate uses [time-limited top-K search](../docs/anytime_top_k_optimizer.md) for both presets. The total search budget includes ordinary attachments, patches/lasers and calibration; shortlists are capped at 256 ordinary and 512 complete builds. Results are best found, with no exhaustive/global-optimum claim.

Run from the project root with Python 3 and Node.js:

```powershell
python tools/builder_server.py
```

Open http://127.0.0.1:8766. Stop with Ctrl+C. No Python or frontend packages need installing. The model modules in `.scratch/calibration-check/` must exist; prepare them with `python tools/verify_calibration_reference.py` if missing.

Builder provides mode/weapon selection, compatible contextual sockets, attachment locks, source calibration positions, live four-panel stats and details, default/current ADS and hip paths, shot count, and JSON export. Optimizer searches the real existing model and opens a result in Builder with tuning retained. Explicitly equipped parts may be locked; required selected parents are included automatically. Locked parts still allow calibration changes. Mode and weapon changes reset the build and locks. The last optimizer run remains available through same-context build edits, calibration and applying outputs; weapon/mode changes and resets invalidate it. Applying a saved result restores its original weapon/mode and tuning. The selected result category is preserved.

The gunsmith supports attachment preview/equip/cancel, contextual sockets, calibration and live detailed stats. The workbench composes installed attachments from source layers; see [weapon composition, fallback behavior and provenance](../docs/weapon_composition.md). [Image loading](../docs/weapon_composition.md#image-loading) documents placeholders and caching, and the [portrait audit](../docs/weapon_composition.md#portrait-audit) covers catalog thumbnails.

The parts list, optimizer results and weapon gallery scroll. Narrow screens provide Parts / Weapon / Stats navigation. For budgets, stat floors, category gates, calibration and search behavior, use the [recoil optimizer contract](../docs/recoil_generator.md) and [agility objective](../docs/agility_optimizer.md). These are the maintained definitions for both the local server and static worker.

Part rows keep their original 76px height and show a compact named stat-delta summary alongside the existing price. Hover or keyboard-focus a part to see equipped/current values, candidate values, signed changes and units in a separate tooltip, with the delta inline after the candidate value, e.g. `60 (+2)`. Matching single/auto vertical and horizontal recoil values share one row per axis; genuinely different values remain separate. No color legend is shown. Green means a modeled benefit and red a trade-off (for example, fewer ADS milliseconds is a green negative). Neutral fields such as fire rate/UI scaling are not assigned an assumed benefit. Hover details are grouped beneath their major stat total: Recoil, Handling, Stability and Accuracy, with Range/Weapon groups for remaining weapon properties. Major labels come from one shared definition. The local server sends `Cache-Control: no-store` for preview assets to avoid stale imported labels. The tooltip compares the actual equipped build with replacing that socket; replacement parts and dependent sockets use default calibration while other valid tuning remains. The current equipped option retains its tuning. Source socket resolution accounts for displaced/coupled parts. Hover does not equip or change the main overview. All changed supported panel, recoil, handling, stability, spread and weapon-stat fields are listed; row summaries show only the four major panel-stat changes (Recoil, Handling, Stability and Accuracy); detailed effects remain in the 400px-wide hover card. Parts with only detailed effects are labeled accordingly. Comparisons are batched per socket and cached by weapon, mode, build, tuning and shot count.

The interaction references the [dfttk builder](https://dfttk.com/demolition/builder); this is an independent local interface, not a modification of the hosted dfttk page. Source: pinned model `20261108-an94-bd-shop.1`. Default/current paths use identical chart scales in model units. The 40/30/30 multiplier proxy remains experimental and within-weapon only. Spam fire uses single/burst proxy modifiers, not measured cadence dynamics. Global/Garena equivalence, final perceived-recoil scoring and prices remain unverified.

Solution overview and result lifecycle follow the [shared preview standard](../docs/solution_preview.md), including score direction, synchronized performance cards and stale-response rejection. Weapon/mode changes and resets clear previous results; same-context edits and tab switches retain them.

Saved builds: **Saved builds** in the toolbar opens the cookie library. Name and save the equipped weapon, or use **Save this build** on an optimizer output without equipping it. Each save includes weapon, mode, attachments, calibration, attachment locks and shot count. The library supports **Load**, **Replace** (using the build shown at the top of the dialog), and **Delete**. Loading restores the weapon/mode and validates the build against the current catalog before applying it; unsupported builds stay saved with an error. Saving retains the previous optimizer run; loading a different weapon/mode invalidates it.

Builds persist in this browser's first-party cookies for up to one year. Clearing cookies removes the library; it does not sync between browsers. The local app stores versioned compact data in chunks below individual cookie limits, with a 32,000-character / 40-cookie total application budget and up to four chunks per build. Replacement writes and checks the new copy before releasing old chunks, and blocked/failed writes show an error. The UI reports storage use and offers **Download current build & model JSON** as a separate backup. Names support Unicode. Cookie data is never treated as trusted catalog input.

Preset objectives are defined in the [recoil contract](../docs/recoil_generator.md) and [agility contract](../docs/agility_optimizer.md). All presets must follow the [shared solution presentation and context lifecycle](../docs/solution_preview.md). The page is named **DF / Weapon Workshop**; main attribute 3 is labeled **Control** throughout the interface.

All presets use shared **exhaustive two-stage top-5% screening**: ordinary attachments first, then patch/laser completions per surviving base, all scored at default calibration. SCIP calibrates only the complete survivors. Generate waits until both exhaustive screens finish before the selected calibration budget starts; Cancel stops either stage. Static Worker progress and local streamed progress show counts and stage changes. Future presets inherit the same search. Screening can discard the best calibrated build, so results remain best found. See the [contract](../docs/exhaustive_staged_screening.md).

UI controls (2026-11-15): equipped parts sort first, then ascending rarity and price. The optimizer's Lock selected attachments toggle captures all explicit equipped attachments, with tuning adjustable; clicking again unlocks them. Empty sockets are not locked. Quick/Standard/Thorough use 5/30/120 second calibration budgets after exhaustive screening. Detonation totals include shop weapon price; Operations totals use dated weapon quotes and report unavailable when absent. Preset display metadata lives in `presetTemplates`, and all presets share constraints and solution rendering. Source and model caveats are in the expandable footer. Response curves use rounded uniform ticks and pointer/keyboard inspection directly on axes.
