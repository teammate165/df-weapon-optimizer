# Weapon workshop

For server-free GitHub Pages hosting, run `python tools/build_github_pages.py`.
The export uses browser Web Workers and external images, with no hosted backend.
See [deployment and validation](../docs/github_pages.md).

Run from the project root with Python 3 and Node.js:

```powershell
python tools/builder_server.py
```

Open http://127.0.0.1:8766. Stop with Ctrl+C. No Python or frontend packages need installing. The model modules in `.scratch/calibration-check/` must exist; prepare them with `python tools/verify_calibration_reference.py` if missing.

Builder provides mode/weapon selection, compatible contextual sockets, attachment locks, source calibration positions, live four-panel stats and details, default/current ADS and hip paths, shot count, and JSON export. Optimizer searches the real existing model and opens a result in Builder with tuning retained. Explicitly equipped parts may be locked; required selected parents are included automatically. Locked parts still allow calibration changes. Mode and weapon changes reset the build and locks. The last optimizer run remains available through build edits, calibration, applying outputs, and changing inputs, weapon or mode, until Generate requests another optimization. Applying a saved result restores its original weapon/mode and tuning. The selected result category is preserved.

The compact gunsmith fills the viewport. Click a socket tile around the weapon to open its compatible parts in the left browser, with source portraits, rarity accents and mod cost. Click a part to preview its stats without equipping it; use Equip or double-click to apply it. Cancel restores the equipped comparison. The workbench follows dfttk placement: rails/sights across the top, muzzle/barrel left, stock parts right, grips/magazine below. Empty/default slot tiles use the source socket glyph; equipped slots use the selected item portrait and its full wrapped name. Riser-provided sight sockets follow immediately to the right of their parent, with each family kept together when wrapping. Calibrate shows every available slider for every equipped tunable attachment, grouped by mounting position, without slider paging. Dragging updates source-model stats and recoil while the slider stays active; pending recalculations coalesce to the newest input. The menu includes live panel scores, ADS time, vertical recoil, camera shake and weapon kick. Four open performance cards below the weapon show every detailed numeric field (31 rows on default M4A1 after merging equal single/auto recoil), including baseline values and breath/spread subfields. Switch the workbench to Recoil for the pattern comparison. The weapon picture is explicitly a base-weapon reference; it is not a rendered composite of installed parts. Empty/default socket glyphs use the locally preserved dfttk icon atlas; unsupported socket IDs fall back to a vector category icon. Part-browser portraits remain item-specific, with category fallbacks for unavailable images.

The parts list, optimizer form/results and searchable weapon gallery scroll. On narrow screens, Parts / Weapon / Stats navigation switches panels, and Core attachments / Rails & optics switches slot groups. Operations uses one maximum attachment budget. Detonation uses the fixed full weapon cap. Priced modes offer automatic no-compromise, cheapest with a 50% improvement gate, and best-value categories. Optional minimum effective Control, Handling, Stability and Accuracy points apply to every result. Calibration is searched before purchasing upgrades and when comparing replacements; cost breaks equal-performance ties even for best performance. Warfare provides Max and marks price-based alternatives unavailable; stat minimums remain enforced. Effective points can differ from the rounded panel; result cards show the effective totals. See [optimizer semantics and module design](../docs/recoil_generator.md).

Part rows keep their original 76px height and show a compact named stat-delta summary alongside the existing price. Hover or keyboard-focus a part to see equipped/current values, candidate values, signed changes and units in a separate tooltip, with the delta inline after the candidate value, e.g. `60 (+2)`. Matching single/auto vertical and horizontal recoil values share one row per axis; genuinely different values remain separate. No color legend is shown. Green means a modeled benefit and red a trade-off (for example, fewer ADS milliseconds is a green negative). Neutral fields such as fire rate/UI scaling are not assigned an assumed benefit. Hover details are grouped beneath their major stat total: Recoil, Handling, Stability and Accuracy, with Range/Weapon groups for remaining weapon properties. Major labels come from one shared definition. The local server sends `Cache-Control: no-store` for preview assets to avoid stale imported labels. The tooltip compares the actual equipped build with replacing that socket; replacement parts and dependent sockets use default calibration while other valid tuning remains. The current equipped option retains its tuning. Source socket resolution accounts for displaced/coupled parts. Hover does not equip or change the main overview. All changed supported panel, recoil, handling, stability, spread and weapon-stat fields are listed; row summaries show only the four major panel-stat changes (Recoil, Handling, Stability and Accuracy); detailed effects remain in the 400px-wide hover card. Parts with only detailed effects are labeled accordingly. Comparisons are batched per socket and cached by weapon, mode, build, tuning and shot count.

Detonation starts by default under its full fixed weapon cap. Operations accepts one maximum attachment budget with dated quotes; missing quotes exclude candidates. Default outputs are **Max**, **Balanced** (automatic knee selection above the 50% quality floor), and **Min** (minimum cost retaining at least 50% of Max improvement). There are no effectiveness inputs. Choices appear in Max, Balanced, Min order; the shared preview shows four separate major-stat cells beneath score and cost. Optional effective Control/Handling/Stability/Accuracy minimums, locks and calibration apply to every result. Duplicate builds are prohibited; missing distinct alternatives are explicitly unavailable. If no positive improvement exists, value categories explain why the gate is unavailable. Warfare returns Max; Balanced/Min explain that priced alternatives are unavailable. Cost excludes the base weapon. See [selection rules and solver assessment](../docs/recoil_generator.md).

The interaction references the [dfttk builder](https://dfttk.com/demolition/builder); this is an independent local interface, not a modification of the hosted dfttk page. Source: pinned model `20261108-an94-bd-shop.1`. Default/current paths use identical chart scales in model units. The 40/30/30 multiplier proxy remains experimental and within-weapon only. Spam fire uses single/burst proxy modifiers, not measured cadence dynamics. Global/Garena equivalence, final perceived-recoil scoring and prices remain unverified.

JSON export preserves IDs, mode, configuration, tuning, model values and source version; it is not an in-game import code.

Stat response curves: the small square info button beside each main stat title opens a per-weapon/per-mode curve calculated for the currently displayed build (including attachment previews). Equipment, calibration and other main stats remain fixed while effective main points are varied with the same source-model intervention used by the research exports. Current effective and displayed points are identified separately. Choose a detailed metric, inspect points, and compare current / +5 / +10 values plus the next +5 gain relative to the previous +5. Exact local flatness is reported for that metric/window, not as a universal attachment or stat cap. Response plots use absolute source performance values; recoil curves use raw multipliers so normalization to the probed default does not falsely cancel the response. These are model probes, not guarantees that every point is reachable by legal attachments.

Saved builds: **Saved builds** in the toolbar opens the cookie library. Name and save the equipped weapon, or use **Save this build** on an optimizer output without equipping it. Each save includes weapon, mode, attachments, calibration, attachment locks and shot count. The library supports **Load**, **Replace** (using the build shown at the top of the dialog), and **Delete**. Loading restores the weapon/mode and validates the build against the current catalog before applying it; unsupported builds stay saved with an error. Loading or saving does not clear the previous optimizer run.

Builds persist in this browser's first-party cookies for up to one year. Clearing cookies removes the library; it does not sync between browsers. The local app stores versioned compact data in chunks below individual cookie limits, with a 32,000-character / 40-cookie total application budget and up to four chunks per build. Replacement writes and checks the new copy before releasing old chunks, and blocked/failed writes show an error. The UI reports storage use and offers **Download current build & model JSON** as a separate backup. Names support Unicode. Cookie data is never treated as trusted catalog input.
