# Optimization algorithms and browser engines

Research updated 2026-11-18. This comparison draws on existing project runs and current primary documentation. The engine choices depend on whether the work is exhaustive ordinary screening, calibration within a fixed layout, or interactive build generation.

## Search contract

The exact ordinary gate covers the grouped, policy-eligible layout population after locks, mounting constraints and budget. Parent-provided sockets, conflicts, grouped aliases, fallback/default choices and bundled replacement behavior affect the legal space. Each layout uses the native default-tune objective. Rank by floor shortfall, the lexicographic objective vector, cost and canonical identity. Retain exactly K = ceil(N/200) ordinary layouts, with N counting layouts represented by the DAG paths. A terminal class can contribute several identities and cross the cut. The tactical gate runs per eligible ordinary base before calibration. A calibrated survivor is a result within the staged search. Demonstrating a global calibrated optimum requires bounding or evaluating the full pre-screening domain. [Ranking contract](../ranking_semantics_research.md), [staged screening](../exhaustive_staged_screening.md), [scoring source trace](../exhaustive_scoring_research.md).

For M4A1 Detonation, Lowest Recoil, Insight locked at path 3/7, and an 800-point cap, the current automatic bipod-grip policy gives **12,268,642** ordinary layouts and **61,344** survivors. The older **12,885,654**-layout dataset has **64,429** survivors. The older full scored run confirmed exact survivor order and fresh native replay, with 695,267 distinct inputs and 2,979,656 objective computations. The latter includes duplicates across workers and recomputations after eviction. Its approximately 187-second optimized phase is a historical Node measurement. Full scored timing for the current population and actual scoring below one million remain unverified. [Current population validation](../../data/optimizer_validation/bipod_grip_policy_20261118/validation.json), [historical cache follow-up](../exact_dag_cache_followup.md).

## Exact algorithms

| Approach | What it can certify | Project fit |
| --- | --- | --- |
| Legal depth-first enumeration | Exact coverage by visiting every eligible layout once, then directly scoring and ranking it. | Independent reference for manifests, counts and replays. Straightforward to shard by disjoint prefixes. Repeated scoring makes it expensive at the full cap. [Reference run](../archive/m4a1_exhaustive_screening_feasibility.md) |
| Layered decision DAG / dynamic programming | Shares equivalent continuations while preserving every incoming path and its identity. An exact weighted selection uses the number of represented paths and reconstructs identities at the rank boundary. | Best fit for the exhaustive gate. State equivalence needs future mounting, cost and lock behavior, native scorer operation order, and exact live state. Proven score-input equality can share scores even when rank or provenance differs. DAG size can still grow exponentially. [Implementation](../optimized_exact_dag.md), [MDD research](https://pubsonline.informs.org/doi/10.1287/opre.2013.1221) |
| Branch and bound / best-first with admissible bounds | Can certify the best result or top K when every discarded branch is provably below the complete rank cut and exact population accounting is separately established. | Useful for a separate best-build query or a calibration subproblem. The exhaustive study requires every layout represented with an exact score, so score-based pruning and dominance are disabled there. Budget or mounting infeasibility bounds can still eliminate illegal branches. [Branch-and-bound paper](https://doi.org/10.2307/1910129), [current policy](../../TODO.md) |
| Constraint programming satisfaction enumeration | Exact finite-domain coverage at exhaustion if the model's projection is bijective over the declared layout identities. | Natural for socket selection, implications, exclusivity, locks and exact integer budgets. Keep source score and rank outside the solver. Auxiliary assignments must be uniquely determined or projected and deduplicated with demonstrated coverage. Solver callbacks and export/marshalling add work, and the solver may enumerate every layout separately. [CP-SAT guide](https://developers.google.com/optimization/cp/cp_solver/) |
| Mixed-integer linear programming / iterative cuts | Certifies the numerical model under its tolerances and termination status. Native replay verifies returned incumbents, and rigorous source-equivalent bounds are needed for an end-to-end proof. | Existing fixed-layout calibration model handles tuning, integer chart steps and supporting cuts. Source binary64 recoil trajectories and tie ordering make a full ordinary-screening translation a much larger project. Repeated MILP incumbent collection has different coverage from satisfaction enumeration. [Calibration model](../scip_optimizer.md), [model and replay comparison](../calibration_engine_benchmark.md) |
| SMT / SAT | Can prove finite legality or equivalence properties given a correct encoding. A projected all-model loop can enumerate legal identities to exhaustion. | Useful for narrowly scoped equivalence checks. Ordered floating-point operators, library math, chart rounding and strict ranking would require a source-faithful encoding. [Z3 floating-point theory](https://microsoft.github.io/z3guide/docs/theories/IEEE%20Floats/), [browser CP and SMT audit](../archive/browser_cp_hosting_research.md) |

## Heuristics for interactive search

| Approach | Potential benefit | Limitation |
| --- | --- | --- |
| Greedy or bounded beam search | Fast first result and predictable search width. Retaining several prefixes can explore competing attachment choices. | A prefix can look weak until it enables a compatible continuation. Width truncation can remove the best build. |
| Multistart neighborhood search with elite seeds | Improve known legal builds and explore alternative basins with independent restarts. Fits bounded interactive Generate and can supply exact-search incumbents. | Single-part neighborhoods can miss coupled changes. Sampling and restart budgets give empirical coverage. [Production anytime search](../anytime_top_k_optimizer.md), [multistart study](../multistart_optimizer.md) |
| Large neighborhood search | Freeze most of a strong build and reoptimize a compatible subtree or a set of interacting slots. | A solved neighborhood certifies its own domain only. Neighborhood selection and rebuild costs need measurement. |
| Simulated annealing or evolutionary search | Can leave a local optimum through stochastic moves or population diversity. | Requires legal moves or repair across dependent sockets, and seeded repeated trials to quantify quality under a deadline. [Simulated annealing paper](https://doi.org/10.1126/science.220.4598.671) |
| Surrogate scoring / fixed shortlist | Saves native evaluations where a coarse score is a useful priority or warm-start signal. | Approximate ranking can lose valid finalists. The historical dominance/shortlist studies used smaller populations and do not certify the current exact percentile. [Layout reductions](../archive/m4a1_layout_reduction_options.md), [dominance prototype](../archive/m4a1_dominance_prototype.md) |

Benchmark interactive methods by time to first replayed legal result, best native objective over time, variation across seeded trials, and exact top-K recall on tractable fixtures. Heuristics can prioritize exact traversal provided complete coverage and the original rank inputs are preserved.

## Browser engines

| Runtime or engine | Browser deployment | Recommended role |
| --- | --- | --- |
| Custom JavaScript / TypeScript | The exact DAG and native scorer already run in independent Workers. TypeScript compiles to JavaScript and can document model/worker contracts. Adding types alone brings no runtime acceleration. | Keep JavaScript as the exact baseline and source scoring implementation. Profile state layout, memo retention, scheduling and serialization before changing runtime. [Current implementation](../optimized_exact_dag.md), [TypeScript type erasure](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types) |
| Custom Rust to WebAssembly | Ship the compiled module and bindings with the static assets. Instantiate one single-thread module per Worker and pass packed buffers in batches. | Prototype a measured hotspot such as key/state interning or weighted selection. Keep native JS scoring in the first experiment. A scoring port needs bit-level comparisons at operation-order, library-math and rounding boundaries, and acceptance on exact identities. Allocation and crossing the JS/WASM boundary can offset kernel gains. [wasm-bindgen guide](https://rustwasm.github.io/docs/wasm-bindgen/), [WASM numerics](https://webassembly.github.io/spec/core/exec/numerics.html), [ECMAScript Math](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math-object) |
| OR-Tools CP-SAT via community portable WASM | Google documents C++, Python, Java and C# installations. The independent cpsat-js portable variant documents synchronous, one-solver-worker all-solutions callbacks, so run each shard in an outer Web Worker. | First off-the-shelf legality-enumeration challenger. Pin and audit the artifact, use a satisfaction model and exact JS scoring, and reconcile projected layout manifests. Measure per-callback overhead and loss of DAG reuse. [Google install guide](https://developers.google.com/optimization/install/), [portable wrapper](https://github.com/owen-lacey/cpsat-js), [alternate community port](https://github.com/Axelwickm/or-tools-wasm) |
| MiniZinc JS | First-party browser WASM interface. MiniZinc compiles the constraint model and delegates search to a selectable solver. Its WASM build instructions list Gecode, Chuffed, CBC and HiGHS integration paths. Verify backend inclusion and all-solutions support in the pinned artifact. | Declarative cross-check or secondary enumeration experiment with a concrete backend such as Gecode or Chuffed. Measure model flattening, solver startup, output decoding and layout projection separately. [Handbook](https://docs.minizinc.dev/en/stable/javascript.html), [build source](https://github.com/MiniZinc/minizinc-js), [solver interface](https://docs.minizinc.dev/en/stable/command_line.html) |
| HiGHS / highs-js | Independent browser WASM wrapper with persistent sparse models and model updates. Locally tested using the pinned highs-js 1.15.4 / native HiGHS 1.15.1 artifact in static Workers. | Leading experimental backend for the existing linearized calibration model. Keep the same model, native replay and cut treatment when comparing with SCIP. [HiGHS](https://highs.dev/), [wrapper API](https://lovasoa.github.io/highs-js/docs/), [project benchmark](../calibration_engine_benchmark.md) |
| SCIP WASM | Existing pinned SCIP 10.0.2 artifact and adapter, validated from static assets. | Calibration reference. It can run the existing primary and conditional Handling phases. Fresh runtime creation and CIP serialization are part of the measured adapter path. [WASM feasibility](../archive/scip_wasm_feasibility.md), [calibration benchmark](../calibration_engine_benchmark.md) |
| GLPK.js | Browser LP/MILP wrapper with JSON input and an LP-only documented solve callback. | Secondary calibration comparator. Check incremental refinement and startup costs if it is tested. [GLPK.js API](https://jvail.github.io/glpk.js/) |
| Z3 JavaScript | First-party WASM binding requires shared memory and relevant browser headers. | Use for targeted equivalence/invariant experiments. Browser hosting and all-model enumeration require additional integration. [Official package documentation](https://github.com/Z3Prover/z3/blob/master/src/api/js/README.md) |

GitHub Pages can serve JS, Worker scripts, WASM and data from a static project path. Ordinary Workers can exchange transferable buffers without shared memory. Internal pthread parallelism adds a cross-origin isolation requirement. Measure startup, download/compile time, per-worker and aggregate memory, cancellation and cleanup at the hosting path expected in use. Each independent solver instance may allocate its own model and heap. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html).

## Decision and comparison gates

1. **Keep the custom exact DAG for ordinary screening.** First measure global terminal-key ownership with retained exact results. On the historical workload, 695,267 distinct scoring inputs show room for reuse, while 2,979,656 actual computations show that merely having enough equivalence does not realize it. Retest against the current population. Compare 8 participating Workers, identical caps and locks, complete identities/score manifests, exact ordered survivors, fresh native replay, and separate counters for distinct inputs, cross-worker duplicate computation and eviction recomputation. Include wall time and memory. [Current backlog and policy](../../TODO.md), [cache follow-up](../exact_dag_cache_followup.md).
2. **Benchmark portable CP-SAT against the same enumeration domain if legal traversal is a substantial cost.** Establish layout-projection parity on small exhaustive fixtures, including nested sockets, shared rails, locked otherwise-excluded parts and cost boundaries. Then compare disjoint shard completion, callback/decode cost, scoring reuse and end-to-end results. MiniZinc with a pinned backend is a useful second declaration of the small fixture and can help expose model mistakes. [CP hosting audit](../archive/browser_cp_hosting_research.md).
3. **Keep SCIP as the calibration reference and HiGHS as the measured challenger.** The historical 16-worker browser benchmark recorded 64 optimal model solves and exact final native objective vectors across all paired runs. HiGHS had the lower median in seven of eight fixture/phase combinations, while SCIP led the complex primary fixture. This measures the full adapters, including persistence and parsing. Compare larger matched survivor cohorts and cases that actually trigger iterative cuts before inferring a broader advantage. [Calibration benchmark](../calibration_engine_benchmark.md).
4. **Keep bounded native anytime search for interactive generation.** A Rust/WASM kernel makes sense if profiling identifies time spent in a kernel with a compact batch interface and parity can be checked against the current implementation. Full scored search on the current domain and broad browser-engine throughput comparisons remain open. [Production search](../anytime_top_k_optimizer.md), [current validation](../../TODO.md).
